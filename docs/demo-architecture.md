## 1. 무엇을 만드나

팀 명세서 그대로 따르되, **화면 배치 하나만 바뀐다.**

| | 팀 명세서 원안 | **확정 (이 저장소)** |
|---|---|---|
| 화면 | 한 페이지를 좌우로 나눠 왼쪽 3D 기기, 오른쪽 폰 프레임 앱 | **기기 페이지와 앱 페이지를 따로 만들고, 서로 다른 기기에서 열어 실시간으로 연결** |
| 예시 | 노트북 한 대에서 둘 다 | 발표 노트북·프로젝터 = 기기 페이지, **실제 휴대폰** = 앱 페이지 |
| 오프라인 | 한 페이지라 그대로 동작 | 같은 노트북에서 두 페이지를 나란히 띄우는 **분할 모드**로 동작 (아래 2-6) |
| 발표 | 노트북 화면 하나 | 프로젝터 = 기기 페이지 + **휴대폰 화면 미러링**. 심사위원이 앱의 경고 화면을 같이 보게 한다 (아래 3절) |

**왜 바꿨나:** 실제 서비스는 "실물 디스펜서 + 휴대폰 앱"이다. 실물 기계는 만들 수 없어서 웹 애니메이션으로 대신하지만,
휴대폰에서 누르면 무대 위 기계가 반응하는 장면이 실제 제품에 가장 가깝고, 발표장에서 가장 눈에 띈다.

나머지(정적 웹, three.js 3D 기기, 가족 4명, 가상 제품명, **추천하지 않고 경고만**, 안전 엔진 T1~T5, 금지어, 데모 시나리오)는 모두 팀 명세서가 기준이다.

### 실행

```bash
cd demo
npm test                      # 엔진·relay 테스트 (Node 22+)
python3 tools/serve.py        # 데모 서버, 오프라인에서도 됨 (휴대폰도 쓰려면 --lan). file:// 로 열면 ES 모듈이 막힘
# python3 -m http.server 는 쓰지 않는다: 연결 대기열이 작아 앱 데이터 로딩이 가끔 실패함
```

| 주소 | 화면 |
|---|---|
| `/app.html?room=demo` | 앱 (휴대폰이면 전체 화면, 넓은 화면이면 폰 프레임 안) |
| `/device.html?room=demo` | 기기 (3D 디스펜서만) |

## 2. 두 페이지 실시간 연결 계획

> 상태: **계획 (구현 전)**. 구현은 `demo/js/relay.js` 한 파일에 모은다. 아래 내용을 바꾸려면 단톡방에 먼저 말한다.

### 2-1. 큰 그림

```
 ┌──────────── 휴대폰 ────────────┐            ┌──────── 노트북 / 프로젝터 ────────┐
 │ app.html                        │            │ device.html                       │
 │                                 │            │                                   │
 │  화면(S1~S10) ── bus ── store   │            │  bus ── device3d.js (애니메이션)  │
 │                  │   (상태 원천) │            │   │                                │
 │               relay.js          │            │ relay.js                          │
 └──────────────────┼──────────────┘            └───┼───────────────────────────────┘
                    │      ① Supabase Realtime (인터넷)  │
                    └───────────────●────────────────────┘
                    │      ② BroadcastChannel (같은 브라우저, 오프라인)
                    └─────────────────────────────────────┘
```

- **앱 페이지가 상태의 유일한 원천**이다. 팀 명세서의 "store가 유일한 원천" 원칙을 그대로 지킨다.
- **기기 페이지는 화면만 그린다.** 상태(칸 배치, 잔량, 기록)를 갖지 않고, 앱이 보내 준 값으로 그린다.
- 두 페이지는 서로의 코드를 부르지 않는다. 각자의 `bus`에 붙은 `relay.js`가 **정해진 이벤트만 상대 페이지의 `bus`로 그대로 옮긴다.**
- 그래서 A(기기)와 B(앱) 담당은 **한 페이지일 때와 똑같이** `bus.on` / `bus.emit`만 쓰면 된다. 연결은 C(또는 relay 담당)만 신경 쓴다.

### 2-2. 어떤 이벤트를 옮기나

이벤트 이름과 페이로드는 팀 명세서 이벤트 계약 그대로다. 여기에 **연결용 이벤트 3개**(★)만 추가한다.

| 방향 | 이벤트 | 페이로드 | 비고 |
|---|---|---|---|
| 앱 → 기기 | `device:load` | `{ productId, slot }` | 명세서 그대로 |
| 앱 → 기기 | `device:dispense` | `{ memberId, round, items: [{ slot, count }], label }` | 명세서 그대로 |
| 앱 → 기기 | `ui:selectSlot` | `{ slot }` | 명세서 그대로 |
| 앱 → 기기 | `device:travel` (Could) | `{ memberId, pouches }` | 명세서 그대로 |
| 앱 → 기기 | ★ `state:sync` | `{ slots, products, members, scenarioDate }` | 기기가 그릴 데이터 전체. 아래 2-3 |
| 앱 → 기기 | ★ `scenario:reset` | `{}` | [시나리오 초기화] 때 기기도 처음으로 |
| 기기 → 앱 | `device:loaded` | `{ productId, slot }` | 명세서 그대로 |
| 기기 → 앱 | `device:dispensed` | `{ memberId, round, at }` | 명세서 그대로 |
| 기기 → 앱 | `device:button` | `{ memberId }` | 명세서 그대로 |
| 기기 → 앱 | `device:slotSelected` | `{ slot }` | 명세서 그대로 |
| 기기 → 앱 | ★ `device:hello` | `{}` | 기기 페이지가 열렸거나 다시 연결됨 → 앱에 `state:sync` 요청 |

이 표에 없는 이벤트(`product:registered` 등 앱 내부 이벤트)는 옮기지 않는다.

### 2-3. 기기 페이지가 데이터를 받는 순서

```
device.html 열림
  └─ relay 연결 → bus.emit('device:hello')         ──▶ 앱: store에서 slots·products·members를 모아
                                                         bus.emit('state:sync', {...})
  ◀── state:sync 수신 → 처음이면 device.init(container, slots), 이후엔 device.updateSlots(slots)
```

- 앱은 **칸이 바뀔 때마다** `state:sync`를 다시 보낸다: `device:loaded`, `device:dispensed`, 제품 등록, 시나리오 초기화 직후.
- 기기가 회전·배출 애니메이션 중에 `state:sync`를 받으면 마지막 값만 들고 있다가 **동작이 끝난 뒤** 반영한다. 5초마다 오는 `state:sync`로 애니메이션 도중에 다시 그려져 끊기지 않게 하려는 것이다.
- 기기 페이지는 `state:sync`를 받기 전까지 "앱 연결을 기다리는 중 · 방 코드 demo" 화면을 보여 준다.
- 기기 앞면의 **구성원 버튼 4개**는 `state:sync`의 `members`로 그린다.

### 2-4. 메시지 봉투

relay가 실제로 주고받는 형태. 화면 코드는 이 형태를 몰라도 된다.

```js
{
  v: 1,                    // 형식 버전
  id: "a1b2c3…",           // crypto.randomUUID() — 중복 제거용
  from: "app" | "device",  // 보낸 페이지
  name: "device:dispense", // 이벤트 이름 (2-2 표에 있는 것만)
  payload: { … },          // 명세서 페이로드 그대로
  at: 1763650000000        // 보낸 시각(ms)
}
```

받는 쪽 규칙:
1. `v`가 1이 아니거나, `name`이 2-2 표에 없거나, `from`이 내 역할과 같으면 버린다.
2. 이미 받은 `id`면 버린다 (두 통로로 같은 메시지가 와도 한 번만 처리).
3. 통과하면 내 `bus.emit(name, payload)`로 넘긴다. 이때 relay가 그 이벤트를 다시 상대에게 보내지 않도록 "원격에서 온 것" 표시를 붙인다 (무한 반복 방지).

### 2-5. 통로 두 개를 동시에 쓴다

| 통로 | 언제 연결되나 | 특징 |
|---|---|---|
| ① **Supabase Realtime broadcast** | `config.js`에 Supabase 주소·키가 있고 인터넷이 될 때 | 휴대폰 ↔ 노트북처럼 **다른 기기끼리** 연결. DB·테이블은 쓰지 않고 신호만 보냄 |
| ② **BroadcastChannel** | 항상 | **같은 브라우저의 탭·창끼리**만 연결. 인터넷 없이 동작 |

- 보낼 때는 **두 통로에 모두** 보내고, 받을 때는 `id`로 중복을 지운다. 그래서 인터넷이 끊겨도 같은 노트북의 두 탭은 계속 연결된다.
- 채널 이름은 `pumix:<방 코드>`. 방 코드는 주소의 `?room=` 값(영문 소문자·숫자·하이픈만, 없으면 `demo`). 발표장에 다른 팀이 있어도 섞이지 않게 발표 직전에 바꿔 쓴다.
- Supabase 연결 코드(예상):
  ```js
  const ch = supabase.channel(`pumix:${room}`, { config: { broadcast: { self: false } } });
  ch.on('broadcast', { event: 'bus' }, ({ payload }) => receive(payload));
  ch.subscribe(status => setStatus(status));   // SUBSCRIBED → 연결됨
  ch.send({ type: 'broadcast', event: 'bus', payload: envelope });
  ```
- `supabase-js`는 ESM 빌드가 하위 패키지를 따로 불러와 로컬 사본이 깨지기 쉽다. `dist/umd/supabase.js`를 `<script>`로 넣고 전역 `supabase.createClient`를 쓰는 것을 권한다(Chart.js도 같은 이유로 `chart.umd.js`). 발표 전에 `demo/vendor/`에 로컬 사본을 둔다.
- **한 방에는 앱 페이지를 하나만 연다.** 휴대폰 앱과 분할 모드 앱이 같은 방에 있으면 상태의 원천이 둘이 되어 갈라진다. 분할 모드 `index.html`은 `?relay=local`로 통로 ②만 쓴다.
- 방 코드는 다른 팀과 섞이지 않게 하는 장치일 뿐 보안 장치가 아니다. anon 키와 방 코드를 알면 누구나 메시지를 보낼 수 있으니 발표 직전에 바꾼다.

### 2-6. 연결 상태 표시와 분할 모드

- 두 페이지 구석에 작은 점을 둔다.
  - 🟢 초록: 다른 기기와 연결됨 (Supabase)
  - 🔵 파랑: 같은 브라우저 안에서만 연결됨 (BroadcastChannel)
  - ⚪ 회색: 상대 페이지가 없음
- 상대가 살아 있는지는 `device:hello` / `state:sync` 주고받기로 확인한다. 기기는 5초마다 `device:hello`를 보내고, 앱은 그때마다 `state:sync`로 답한다. 10초 동안 답이 없으면 회색.
- **분할 모드 `index.html`**: `app.html`과 `device.html`을 `<iframe>`으로 나란히 띄운다. 두 iframe은 같은 브라우저라 ②로 연결되므로 **인터넷 없이** 팀 명세서 원안의 한 화면 배치가 그대로 나온다. 리허설, 와이파이 장애, 녹화용.

### 2-7. 동시 실행과 막힘 방지

- **기기 쪽**: 팀 명세서대로 동작 중에 들어온 `device:*` 요청은 큐에 쌓아 순서대로 처리한다.
- **앱 쪽**: 배출을 보낸 뒤 `device:dispensed`가 올 때까지 배출 버튼을 잠근다. 단, **15초 안에 답이 없으면** 잠금을 풀고 "기기 응답이 없어요" 안내를 띄운다. 기기 페이지가 닫혀 있어도 앱이 멈추지 않게 하려는 것이다. 이때 잔량은 줄이지 않는다.
- **기기 버튼**(`device:button`): 앱이 연결돼 있지 않으면(회색) 기기 화면에 "앱이 연결되지 않았어요"를 짧게 보여 주고 아무것도 하지 않는다. 조합을 아는 건 앱뿐이기 때문이다.

### 2-8. 설정과 키

```js
// demo/js/config.js
export const SUPABASE_URL = '';      // 비워 두면 통로 ②만 사용
export const SUPABASE_ANON_KEY = '';
```

- Supabase 무료 프로젝트 하나를 만들고 **Project Settings → API**의 `Project URL`과 `anon public` 키만 넣는다. 테이블은 만들지 않는다.
- `anon` 키는 원래 브라우저에 공개되는 용도의 키이고, 이 프로젝트에는 데이터가 없어서 신호만 오간다. 배포된 사이트에서 휴대폰이 접속하려면 이 값이 페이지에 들어 있어야 하므로 **`config.js`에 넣어 커밋하는 것을 제안**한다. (팀이 반대하면 `config.local.js`로 빼고 배포 때만 넣는다 — 열린 결정)
- LLM API 키 같은 **비밀 키는 절대 커밋하지 않는다.**

### 2-9. 휴대폰에서 여는 방법

| 방법 | 언제 | 설명 |
|---|---|---|
| **배포 주소** | 발표 (추천) | `demo/` 폴더를 Vercel(또는 GitHub Pages)에 정적 사이트로 배포. 휴대폰은 `https://…/app.html?room=xxx`, 노트북은 `…/device.html?room=xxx` |
| 같은 와이파이 | 개발 중 | 노트북에서 `python3 -m http.server 8000` → 휴대폰에서 `http://<노트북 IP>:8000/app.html`. 공용 와이파이는 기기끼리 접속을 막는 경우가 많아 발표 때는 배포 주소를 쓴다 |

앱 페이지 상단 바에 방 코드를 보여 주고, 기기 페이지 대기 화면에는 앱 주소를 QR 코드로 띄우면 발표 때 휴대폰으로 바로 들어갈 수 있다 (Could).

### 2-10. 만드는 순서와 확인 방법

분할 모드를 Supabase보다 먼저 만든다. 오프라인 대비·리허설·녹화에 모두 필요하고, 휴대폰 시연(Supabase·배포)은 그다음이다. 22:00~23:00은 5분 스피치라 개발은 23:00부터, 1차 통합은 01:00이다.

| 순서 | 할 일 | 확인 |
|---|---|---|
| 1 | `relay.js`: 봉투 만들기·검사·중복 제거 + 통로 ②(BroadcastChannel) | 같은 브라우저 두 탭에서 `bus.emit('device:dispense', …)` → 다른 탭에서 수신. 이상한 봉투(이름 없음, 모르는 이름, 내 역할)는 무시 |
| 2 | `device:hello` ↔ `state:sync` 주고받기, 연결 점 | 기기 탭을 나중에 열어도 칸이 그려짐. 앱 탭을 닫으면 10초 뒤 회색 |
| 3 | 분할 모드 `index.html` (`?relay=local`) | 인터넷 끄고 명세서 데모 시나리오 완주. **01:00 1차 통합은 이 모드로** |
| 4 | 통로 ①(Supabase) 추가 | 휴대폰 ↔ 노트북에서 1초 안에 반응. 와이파이를 끄면 분할 모드는 계속 동작 |
| 5 | 배포 + 실기기 리허설 | 실제 휴대폰으로 시나리오 완주, [아빠] 버튼 연타·배출 연타 때 순서대로 처리 |

## 3. 발표 구성 (심사위원이 앱 화면을 보게)

이 서비스의 핵심인 경고·근거·상담용 목록은 **앱 화면**에 뜬다. 휴대폰으로만 조작하면 심사위원은 프로젝터의 기기만 보게 된다.

| 구성 | 방법 |
|---|---|
| 기본 | 프로젝터 왼쪽에 `device.html`, 오른쪽에 **휴대폰 화면 미러링 창**. 발표자는 휴대폰을 조작하고 심사위원은 두 화면을 같이 본다 |
| 안드로이드 미러링 | 노트북에 scrcpy 설치 → USB 디버깅 켜고 케이블 연결 |
| 아이폰 미러링 | Mac의 QuickTime Player → 새로운 동영상 녹화 → 카메라를 iPhone으로 선택 (케이블) |
| 기본 (11-21 결정) | 노트북 한 화면(`/`)에 왼쪽 기기 + 오른쪽 아이폰 틀 앱. 인터넷 없이 동작 |

- 미러링은 22:00 전에 발표 노트북과 휴대폰 조합으로 한 번 시험한다.
- 데모 순서 제안(judge 평가 반영, 약 2분): 훅 한 문장 → 영문 해외 직구 유산균 라벨을 AI가 판독(`Contains: Milk` → 우유, 확인 필요 항목은 사용자가 확인) → 휴대폰에서 투입 → 프로젝터의 기기가 서늘 칸으로 회전·이송 → 가족 경고(서윤 알레르기, 아빠 항응고제) → 약사·의사에게 보여 줄 상담용 복용 목록 → 엄마 아연 상한 96% 근거 → 기기의 [아빠] 버튼으로 배출 → 영양 정보·기록 요약.
- 휴대폰 → 기기 반응 장면이 첫 30초 안에 나오게 한다. 실제 제품 구조(실물 디스펜서 + 휴대폰 앱)를 가장 잘 보여 주는 장면이다.
